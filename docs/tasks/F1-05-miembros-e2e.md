## Entregables
1. **Miembros** `src/app/(app)/o/[slug]/settings/members/page.tsx` (`requireRole(slug, 'owner','admin')`): tabla con `src/components/data-table/` (TanStack Table v9: `useTable({ data, columns, features })` + `tableFeatures({...})`; **no** copies la guía v8 de shadcn: lee `node_modules/@tanstack/react-table/skills/`) con correo, rol, fecha de alta; orden y paginación por URL (`searchParams` validados con Zod: `page ≥ 1`, `pageSize ≤ 100`, `sort` de una lista cerrada). Acciones en `features/members/actions.ts`: cambiar rol (`Select`), quitar miembro (confirmación con `Dialog`). Errores de la base como mensajes: `23514` → «La organización necesita al menos un propietario»; `42501` → «No tienes permiso para esta acción». Edición concurrente: no aplica (una sola columna editable). La UI oculta lo que el rol no puede, pero la autoridad es RLS + `requireRoleForAction`.
2. **Invitaciones** en la misma página, debajo: lista de pendientes (correo, rol, caduca, botón «Copiar enlace» y «Revocar»), formulario correo + rol (owner solo visible y permitido para owners). `features/invitations/actions.ts`: `createInvitation` genera 32 bytes con `crypto.getRandomValues`, guarda `token_hash` (SHA-256 hex del token en UTF-8, con `crypto.subtle.digest`) y `created_by = user.id`, y devuelve la URL `/invitations/<token>` en el resultado para que la UI la muestre una sola vez (D-017 pendiente: sin envío de correo en esta fase; registra esta decisión como D-026 en `docs/DECISIONS.md`, estado Aceptada, con el porqué: el proveedor de correo aún no está elegido y el enlace copiable desbloquea el flujo). `revokeInvitation` borra la fila. Correo duplicado pendiente (índice único parcial) → `fieldErrors.email`.
3. **Aceptar** `src/app/(app)/invitations/[token]/page.tsx`: sin sesión → `/login?next=/invitations/<token>` (y `/signup` enlazado con el mismo `next`); con sesión, botón «Unirme» que llama a `rpc('accept_invitation', { token })` y redirige a `/o/<slug>`; error → mensaje «Invitación inválida, caducada o para otro correo» (no distingue cuál: no filtrar información). El token nunca se registra en logs ni se persiste en claro.
4. **Auditoría**: las acciones de la app escriben en `audit_log` con `actor_user_id = user.id`, `actor_kind = 'user'` y acciones fuera de los prefijos reservados (`members.role_changed`, `members.removed`, `invitations.created`, `invitations.revoked`). Página `settings/audit` (owner/admin) con las últimas 100 entradas, solo lectura.
5. **E2E Playwright** (`e2e/`): `auth.setup.ts` crea con la API admin (`SUPABASE_SECRET_KEY`, `email_confirm: true`) un usuario por rol más uno sin membresía, crea la organización llamando a `create_organization` con el cliente del owner, inserta las membresías de los demás con el cliente admin (clave de servicio), inicia sesión por la UI y guarda `e2e/.auth/<rol>.json`. Specs: login válido e inválido · registro · crear organización (slug repetido muestra error) · owner invita, copia enlace, un usuario nuevo acepta y aparece como miembro · admin no ve la opción owner y la acción lo rechaza · cambio de rol y último owner no degradable · viewer no accede a `settings/members` (`/no-access`) · usuario sin membresía ve `/no-access` · sesión revocada: tras borrar la membresía, la siguiente navegación cae en `/no-access` · recorrido de las vistas principales sin ningún `securitypolicyviolation` (listener instalado con `page.addInitScript`). Selectores por rol y etiqueta (`getByRole`, `getByLabel(…, { exact: true })`); `getByRole('alert')` filtrado por texto.
6. **Lighthouse** `lighthouserc.cjs`: `startServerCommand: "npm run start"`, URLs `/o/<slug>` y `/o/<slug>/settings/members` con cookie de `e2e/.auth/owner.json` en `settings.extraHeaders`, `numberOfRuns: 3`, sin `preset`; asserts `categories:performance ≥ 0.9`, `categories:accessibility ≥ 0.9`, `largest-contentful-paint ≤ 2500`, `total-blocking-time ≤ 200`, `cumulative-layout-shift ≤ 0.1`.
7. **CI**: en `.github/workflows/ci.yml`, tras `npm run build` del job `db`: `npx playwright install --with-deps chromium`, `npm run test:e2e`, `npm run lhci`, y `actions/upload-artifact@v7` con `playwright-report/` si falla. Si el CI exige que `supabase start` exponga `inbucket`/correo, no hace falta: no se envían correos.
8. Tests Vitest de los esquemas nuevos (members, invitations, searchParams) y del helper que genera el token y su hash (hash conocido para una entrada fija).

## Reglas
- Estados obligatorios en cada vista: cargando (`loading.tsx`), vacío («Aún no hay invitaciones»), sin permiso, error.
- Doble envío: botón deshabilitado mientras `isSubmitting`. Sesión caducada a mitad de formulario: error como dato y formulario intacto.
- Nada de `useEffect` para datos; sin TanStack Query. Copy en español, código en inglés. Dinero no aplica aquí; fechas con `Intl.DateTimeFormat('es-MX')`.
- No puedes ejecutar E2E ni Lighthouse en el sandbox (sin Supabase): verifica `typecheck`, `lint`, `test`, `build` y que `npx.cmd playwright test --list` enumera los specs sin errores de sintaxis. El CI los ejecutará.
